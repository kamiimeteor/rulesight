## 2026-10-29

**插件方案：`/rulesight:rulesight` 做成 skill；判定改成调用用户自己的 `claude -p`，不再用 Agent SDK；要求用户先装 Node。**
- 判定方式：查官方文档，子 agent 没有办法保证输出结构化 JSON，最多 20 个并行，撑不起一百多段的长会话和合并；`claude -p --json-schema` 可以。原来定的"判定子 agent"改掉。
- 条款：文档不允许第三方提供 claude.ai 登录、代用户走订阅额度或碰凭证，"基于 Agent SDK 的产品"也包括在内；但允许"用户用自己的订阅登录官方原版 Claude Code"。插件调用用户自己装的 `claude -p`、不碰任何凭证，更接近允许的情形。文档没有明说插件可以这样做，公开发布前要再确认一次。
- 运行环境：官方推荐的安装方式不带 Node。我选了要求用户先装 Node（不做独立程序）：省事、跨平台；插件检查不到 Node 时告诉用户怎么装。脚本发布时打包成普通 JS，Node 18 以上能跑。
- 会话：插件用 `${CLAUDE_SESSION_ID}` 拿当前会话 ID。文档提醒 JSONL 是内部格式、每个版本都可能变；应对办法是按 Claude Code 版本留测试样本，读不懂时清楚报错，不悄悄判错。
- 斜杠命令是旧写法，用 skill 做。

**分段判定完成；用正式流程重测第二轮的 3 个真实场景，3 个都抓到。步骤格式升到第 2 版（加 `at`）。**
- 3 个场景各判出事前约 7 小时（按时间段判，范围内 735 到 2068 步，切 3 到 9 段），全部抓到：两次"又用英文"、一次"在还没发布的菜谱收藏页上反复修"。上一轮用 120 步的片段时收藏页那个漏了；这次范围里一个子 agent 的步骤写明了"收藏页默认隐藏"，以前用 SDK 读不到这个子 agent。前情起了多大作用这次分不出来。
- 还额外报出 2 处违反，核对后都是真的：一个子 agent 想用 `git commit --amend` 改写提交被拦下，随后改用 `git reset HEAD~1` 重新提交，reflog 证明历史还是被改了；主 agent 读了项目外的会话记录，我确认算违反：为了找上下文去读别的会话，不算任务需要。
- 实际记账 $7.08（17 段），比预想的高；按 $3/百万字的估算偏保守但量级对。
- 报告页原来把整份会话原文塞进页面，2.6 万步的会话生成 422MB 的报告，浏览器打不开。改成只放判定范围内的步骤，且只有被引用的步骤保留原文，降到 0.7 到 1.6MB；页头的时间和进度条起点也按判定范围显示。
- 按时间段判时，范围之前的步骤也用来算第一段的前情。

**长会话分段判定：默认判整份，超过 10 段先报价；子 agent 的每一步都判。**
- 实测：一份 54 天的会话读全有 1950 万字，按每段约 20 万字要切约 80 段，按之前的单价估 $15–40；只看主会话也要约 27 段。判定走用户自己的订阅额度，所以跑之前必须先告诉用户要切几段、大约多少钱、多久。
- 子 agent 也全部判：第一轮测过子 agent 自己也会违反规则（"子 agent 只能读文件"），只看它交回的报告会漏掉。代价是长会话段数约 3 倍。
- 切段优先在压缩点和用户发言处，不拆开工具调用和结果。每段带上前情：之前最近的一次压缩摘要和用户最后 5 句话，标明"只用来理解，不能当证据"（针对第二轮那个"收藏页没发布"的漏报）。
- 合并：任一段违反即违反，关键步骤取第一次，其他段的违反列进证据；否则任一段遵守即遵守；都没有就是不适用。每段原始结果都留在判定文件里。

**自己读 JSONL 的适配器完成，长会话能读全。**
- 读全以后：一份压缩过 8 次的长会话从 SDK 的 493 次工具调用变成 5765 次（主会话）加 288 个子 agent 的 1.5 万次；之前丢的子 agent 并行调用结果全部回来了（49/49）。
- 自检脚本直接对照原始文件核数量，10 份测试会话都通过；第一轮的 27 条答案已知规则在新步骤上重跑，全对。
- 原始格式里三处我原来判断错的，靠实测改正：用户在 agent 干活时插的话存在 `attachment` 条目里，不能跳过；`isMeta` 的条目里也有子 agent 交回的报告；`/loop` 这类斜杠命令的参数就是用户的指令。
- 615MB 的会话读取约 6 秒，内存峰值 3.6GB；读出的步骤文件 434MB，离 Node 单个字符串上限不远。下一步必须做分段判定。

**第二轮测试结果（真实会话，误报 + 漏报）。样本小，比例只作参考，重点是三类失误。**
- 误报：3 份会话共报出 2 处违反，我核对后 1 真 1 假。假的那处：我问"下一步还有什么建议"，agent 列完建议再问"要不要现在做"，判定当成"不必要地要确认"。它没分清我上一句是在提问还是下指令。
- 漏报：从我在会话里亲口纠正 agent 的记录里，找出 3 个能对应到成文规则的场景（2 次"又用英文回复"、1 次"在还没发布的菜谱收藏页上反复修"）。截取纠正前 120 步、去掉纠正那句，规则混进 10 条无关规则，每个跑 2 次。英文的 2 个两次都抓到；收藏页的两次都判"不适用"——片段里没有任何地方说收藏页还没发布，判断要靠会话以外的事实。混进去的无关规则 6 次都没误报。
- 找出事场景时还发现：这些场景全在 SDK 读不到的长会话前段里，见上一条决定。
- 要改的三处：会话读全（已决定自己读）；判定区分"提问"和"指令"；分段判定时要带上前面的关键背景，或者让规则能写明"某功能还没上线"这类事实。前两处等例子多了再改提示词，免得只凭一个例子改过头。

**会话读取改成自己读 JSONL，不再用 Agent SDK 的 `getSessionMessages`。推翻 10-28 的决定。**
- 原因：SDK 读长会话时只返回最后一次压缩后沿消息链能走到的部分。一份 9/3 到 10/27 的会话（压缩 8 次）只读回最后两天，约 9% 的工具调用；另外两份长会话只读回 5% 和 34%。我在会话里亲口纠正过 agent 的 4 个场景，全部落在读不到的部分。
- 这是同一个前提第二次被推翻：10-28 已经发现 SDK 会丢子 agent 并行调用的分支，当时接受的前提是"读出来的大体完整"。
- 真实用户最需要检查的，恰恰是连续用了很多天的长会话。
- 做法：把整份文件（含子 agent 文件）的条目按时间排序、按 uuid 去重，不沿消息链回溯。步骤格式不变，判定和报告页不用改。
- 后续要做：长会话放不进一次判定，需要分段判定（按时间或压缩点切段，再合并结果）。
- 代价：Claude Code 改日志格式时要自己跟着改。

**一致率不再靠逐条复核，改成两个数：误报率和漏报率。**
- 试过逐条复核：3 份会话 91 条判定，大多数是一眼就能判的"不适用"和"遵守"。点到第 11 条我就没在细看、一律点"判对了"了。这样得出的一致率是假的，那 11 条作废。
- 误报率：报告报出的违反里，有多少是真的。只看违反的卡片，每份会话通常 0 到 3 张，这也正是真实用户会看的部分。
- 漏报率：我记得的真实"出事"场景里，有多少被抓到了。我说出场景，找到对应会话跑判定。
- 2 月的"一致率 80%"按这两个数来衡量。逐条复核模式只留给校准用，用户版报告里只留一个不起眼的"这条判错了？"，以后再改。

**第一轮判定测试（答案已知的规则）：通过。判定输出改成先写理由、再下结论。**
- 做法：3 份类型不同的会话（会话 B 写代码跑测试、C 写个人博客文章且思考有正文、D 带 2 个子 agent），每份配 9 条答案事先从步骤里核实过的规则，违反 / 遵守 / 不适用各 3 条，顺序打乱。sonnet 每份跑 2 次，用 `scripts/score.ts` 对答案打分。
- 旧字段顺序（先结论后理由）：修正我自己答案里的 3 处错误后，54 次判定结论对 52 次。真错 1 次：理由写着"不符合规则"，结论却选了"遵守"；另 1 次是规则本身有歧义。
- 改成先写理由、再写证据步骤、最后下结论之后：54 次全对，两次结果完全一致，关键步骤都指在合理位置。
- 之前担心的两点这次没问题：会引用子 agent 的步骤（5.10），也会引用思考步骤。
- 局限：这些规则比真实规则简单、答案明确，样本也小。真实规则的准确度要靠第二轮人工复核。
- 我出错的地方值得记住：答案文件漏了几个同样合理的关键步骤，还有一条规则写成了"原样转告"，agent 实际是转述，按字面判定是对的。设计规则和答案时要比判定更严格。
- 新发现：Sonnet 5.5 的安全过滤器误拦过一次正常的博客写作会话（判定直接失败），原样重试就过了。插件要处理这种失败：自动重试，必要时换模型。

**测试会话只放 `private/`，文档里不写来源项目名、会话 ID 和具体内容；第一次公开推送前，用全新的 git 历史重建仓库。**
- 原因：测试会话来自本机的真实项目，可能含私人信息，会话里还可能有明文密码。之前的提交里写过会话 ID 和项目名，仓库还没推送过，所以现在先匿名化，公开前再把旧历史整个换掉（换之前先确认）。
- 文档里用"会话 A、B……"指代测试会话。

**报告页第 2 版：React + shadcn/ui，打包成一个离线 HTML；布局改成分页列表 + 两栏等高。**

- 组件用 shadcn/ui（我的要求）。它是 React 组件，所以加了 Vite 构建，用 vite-plugin-singlefile 打成一个 HTML 模板；生成报告时只往模板里塞数据，不用重新构建。小会话的报告 452KB，202 步的会话 983KB。
- 左边原来是一长串三层卡片，规则一多左边很长、右边很空。改成顶部分页（违反 / 遵守 / 不适用）+ 每条两行的紧凑列表，两栏一样高、各自滚动。
- 进度条原来同时讲"哪里违反"和"当前规则的证据"，用黑色块和圆点都不清楚。改成只讲当前规则：判定依据实色加高并标出步骤号，其他证据浅色加高；别处的违反只留一个可点击的小三角。
- shadcn 组件源码直接从官方组件库下载放进 `report/src/components/ui/`，没让它的命令行工具装依赖：它想另起一套依赖，还要装一个叫 `cn` 的包，而那只是组件源码里的占位写法。
- 会话内容只当文字渲染（React 默认转义，不用 `dangerouslySetInnerHTML`）；塞数据时转义 `<` 和 U+2028/2029，测过含 `</script><script>` 的会话文本不会被执行。

**判定原型跑通：sonnet，本机 Claude Code 登录，一次调用判完全部规则。**
- 调用方式：Agent SDK `query()`，`tools: []`（只读，什么都改不了）、`persistSession: false`（不留会话记录）、`settingSources: []`。最后这项必须设：不设的话，判定 agent 会把用户自己的 CLAUDE.md 和 hooks 当成它的指令加载进来。
- 规则提取不调模型：每个列表项、每个表格行算一条，记文件和行号。列表前以冒号结尾的引导句（如 "Never do any of the following:"）拼到每条前面，不然意思会反过来。已知漏掉：不是列表项的段落式规则（全局 CLAUDE.md 里有 4 条）。
- 校验器：遵守、违反必须引用存在的步骤，否则丢掉，不编造；每条规则最多一个判定。
- 第一次实测（测试会话 A 对照全局 CLAUDE.md，56 条规则）：遵守 22、违反 0、不适用 34，被拒 0，68 秒，记账 $0.44。
- 抽查 6 条，5 条判得对。判错 1 条：agent 想读含 token 的 MCP 配置，被 Claude Code 权限检查拦下，判定 agent 却判成"遵守"，把拦截的功劳算给了 agent。
- **决定：被权限系统、沙盒拦下的违规尝试也算违反。** Rulesight 回答的是"agent 有没有照规则做"，不是"最后有没有出事"；守住规则的是系统，不是 agent。这类事在 Claude Code 里一闪而过，不写代码的用户最难自己发现。已写进判定提示词，卡片标题写"试图……，被系统拦下"。
- 改完重跑：这条变成违反（第 22 步）。但另外 5 条和改动无关的规则也变了（55 条里变了 5 条，自洽率约 91%），基本都在"遵守 / 不适用"的分界上，还有 1 条边界情况从遵守变成违反（清理完又问一次"接着移植吗"）。说明同一模型两次判定本身就有约 9% 的出入；校准一致率时要把这部分算进去，不能只跑一次。
- 引用的证据全是主会话步骤，85 个子 agent 步骤一次都没被引用，还没查原因。

**Claude Code 适配器原型完成；第一份测试会话（下称会话 A）取自本机的一个项目。**
- 读 `private/`：把 `CLAUDE_CONFIG_DIR` 设成 `private/claude-home`，在 SDK 加载前设置；文件按 `projects/<任意名>/<sessionId>.jsonl` 放。SDK 的 `dir` 参数只能指项目目录，指不到任意文件夹。没用 `sessionStore`：它是 alpha 接口，还得自己逐行读 JSONL。
- 运行方式：Node 24 直接跑 `.ts`，不用 tsx（沙盒挡住了它的 IPC 管道）。
- SDK 会丢子 agent 并行调用的部分结果（见 `docs/step-format.md` 的已知限制）。决定：暂时接受，继续只用 SDK。判定原型跑起来以后，如果常因此误判，再考虑破例自己读子 agent 的 JSONL。

**步骤格式第 1 版定稿，见 `docs/step-format.md`。**
- 工具调用和它的结果合成一步：报告能直接写“运行命令 npm test → 3 个失败”，步骤数大约减半。
- 思考内容也算步骤：“我先跳过测试”这类话常常只在思考里出现。
- 子 agent 的步骤编成 12.1、12.2，挂在启动它的那一步下面，主会话步骤号不受影响；所以步骤号统一用字符串。
- 单个步骤不记时间：官方 SDK 返回的消息里没有逐条时间戳。

**目标用户改成用 Claude Code 但不写代码的设计师、产品经理和创业者。**
- 原来是个人开发者和设计工程师。工程师能自己读代码和 diff 来核实，也已经有 heeded、showwork；不写代码的人只能相信 agent 的话，痛点更强。
- 正好对上两个差异点：他们写不出正则，需要自然语言规则；看不懂命令行表格，需要给人看的报告。

**第一版做成 Claude Code 插件，判定用用户自己的 Claude Code。**
- 用户输入 `/rulesight:rulesight`：脚本把日志整理成步骤（不调用模型）→ 单独的判定子 agent（上下文全新、只读）逐条判定 → 生成报告页并打开。
- 不用 API key 做默认：目标用户大多没有 API key。Agent SDK 文档写明第三方产品不能提供 claude.ai 登录或额度，所以独立工具走不通，插件里让用户自己的 Claude Code 判定可以。
- API key 只用于校准测试，固定模型。
- 不做 MCP：结果是给人看的，最后还是要打开报告页。不让被检查的会话自己判定：那等于自己给自己打分。

**会话读取用 Anthropic 官方 Agent SDK（`getSessionMessages`），技术栈用 TypeScript。**
- 官方维护，Claude Code 改日志格式时会跟着更新；能读子 agent 和压缩边界。在本项目的会话上实测读出 76 条消息，工具调用和结果都在。
- 备选：daaain/claude-code-log（Python，MIT，1250★），但它是转换工具，`load_transcript` 是内部接口，依赖也重。
- 代价：SDK 是 Anthropic 商业条款，不是严格意义的开源；`message` 字段没有类型，要自己写。
- 还没验证：怎么读 `private/` 或示例目录里的 JSONL 文件。

**发现两个直接竞品，定位要收窄。**
- heeded：不用 LLM，规则写成 JSON 正则，统计每条规则的遵守率，命令行输出。示例里也有“完成前必须跑测试”这条规则。
- showwork：对 agent 声称完成的结果做确定性检查，每次会话出一份收据。
- 结论：只说“检查 agent 有没有遵守 CLAUDE.md”已经不够。差异只能来自两点：自然语言规则加 LLM 判定，以及附带证据、给人看的报告。
